在 PostgreSQL 中，事务是一组数据库操作的逻辑单元，这些操作要么全部成功执行，要么全部不执行，以确保数据的一致性和完整性
# 事务的基本概念

- 定义：事务是一个不可分割的工作单元，由一条或多条 SQL 语句组成 { 数据查询（`SELECT`）、数据修改（`INSERT`、`UPDATE`、`DELETE`）、数据定义（`CREATE`、`ALTER`、`DROP`）等操作 }

- 特性（ACID）
    - 原子性（Atomicity）  —— 由事务CLOG与可见性规则保证
         事务中的所有操作要么全部成功提交（`COMMIT`），要么全部回滚（`ROLLBACK`），不会出现部分执行的情况
    - 一致性（Consistency）—— 由约束、原子性、隔离性……共同保证
         事务执行前后，数据库的完整性约束（如主键约束、外键约束、唯一约束等）保持不变
    - 隔离性（Isolation） —— 由 MVCC 与 隔离级别保证
         多个并发事务之间相互隔离，一个事务的执行不会影响其他事务。不同的隔离级别决定了事务之间可见性和干扰程度
    - 持久性（Durability）—— 由WAL保证
         一旦事务成功提交，其对数据库的修改将永久保存，即使系统崩溃或发生故障。这通过日志记录（WAL）来实现，确保已提交的事务不会丢失

# txid 与 回卷问题
- txid: 每个事务在开始时都会分配一个32位的无符号整数作为id，取值空间可以到42亿，将取值空间作为一个环，某个id前21亿/取值空间一半是过去已分配的txid, 后21亿/取值空间一半是之后分配的txid
     其中 txid=0 是无效txid
         txid=1 是初始启动时的事务id
         txid=2 是冻结的txid，比任何txid都旧，由VACUUM处理
 ![[Pasted image 20260924232536.png]]
 - 事务回卷问题：长时间运行，txid从开始的n，运行到了2^31 +n+1,导致n的元组变成未来事务的操作，不可见。通过在t_infomask中置冻结txid=2 解决

# 事务的操作语句

- 开始事务
     在 PostgreSQL 中，默认情况下，每个单独的 SQL 语句本身就是一个事务。
     但如果要将多个 SQL 语句组合成一个事务，可以使用`BEGIN`、`START TRANSACTION`或`BEGIN TRANSACTION`语句开始一个事务

```sql
BEGIN;
-- 或
START TRANSACTION;
```

- 提交事务
     使用`COMMIT`语句将事务中所有的修改永久保存到数据库中。
     一旦执行`COMMIT`，事务中的操作就无法回滚
```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 100 WHERE account_id = 2;
COMMIT;
```

- 回滚事务
     使用`ROLLBACK`语句撤销事务中所有未提交的修改，将数据库恢复到事务开始前的状态在, 事务执行过程中发现错误或不满足某些条件时，可以回滚事务
```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;
-- 检查余额是否足够，若不足则回滚
SELECT balance FROM accounts WHERE account_id = 1;
-- 假设余额不足
ROLLBACK;
```

# 保存点（Savepoints）/子事务（Subtransaction）

- 定义
     保存点是事务中的一个标记点，可以在事务内设置多个保存点 
     通过设置保存点，可以将事务部分回滚到特定的标记位置，而不是回滚整个事务
 
- 操作语句
     使用`SAVEPOINT`语句创建保存点，例如`SAVEPOINT my_savepoint;` 
     使用`ROLLBACK TO SAVEPOINT`语句回滚到指定的保存点，如`ROLLBACK TO SAVEPOINT my_savepoint;`
     使用`RELEASE SAVEPOINT`语句删除保存点，如`RELEASE SAVEPOINT my_savepoint;` 
```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;
SAVEPOINT update_account1;
UPDATE accounts SET balance = balance + 100 WHERE account_id = 2;
-- 发现错误，回滚到第一个更新操作之后的保存点
ROLLBACK TO SAVEPOINT update_account1;
RELEASE SAVEPOINT update_account1;
COMMIT;
```
# 异常处理与自动回滚

- 异常处理
     在事务执行过程中，如果发生错误（如违反约束、语法错误等），PostgreSQL 会根据错误的严重程度和事务的状态进行处理。
     - 对于一些严重错误，事务会自动回滚
    -  对于一些可恢复的错误，可以通过异常处理机制（如`EXCEPTION`块，在 PL/pgSQL 中使用）来捕获和处理错误，决定是否回滚事务

- 自动回滚
     如果在事务中执行的 SQL 语句违反了数据库的完整性约束（如插入重复的主键值）、发生了内部错误（如内存不足）或超出了资源限制，PostgreSQL 会自动回滚事务，确保数据库的一致性
```sql
BEGIN; INSERT INTO unique_table (unique_column) VALUES ('duplicate_value'); -- unique_column有唯一约束 -- 由于违反唯一约束，事务会自动回滚
```

# 多事务（MultiXact）

同一行需要同时被多个事务以共享方式锁定，一个 XID 无法表达多个事务共同持有锁，于是 PostgreSQL 引入了 MultiXact

t_xmax与t_infomask记录多事务
- 一个全局递增的 **MultiXact ID（mxid）** 来标识。
- 当一行首次被并发多个事务共享锁定时，就分配一个 mxid，并将这组 XID 写入 `pg_multixact_members` 目录。

# 两阶段提交(2PC)事务

分布式事务（跨多个客户端/会话）要求原子性，需引入两阶段提交

- **阶段一（Prepare）**
     各参与者把事务执行到可提交点，写 REDO/UNDO，持久化到磁盘并释放相关资源前的最后屏障
     各参与者执行prepare transaction '2pc_trans'是第一阶段提交；PREPARE 时使用同一个 GID 字符串
     掉线或者回滚视作未提交
- **阶段二（Commit/Abort）**
     根据结果（是否有参与者未提交），命令所有参与者统一提交或回滚
     执行COMMIT  PREPARED  '2pc_trans' 是第二阶段提交
     执行ROLLBACK PREPARED '2pc_trans'  是第二阶段回滚
 
一阶段提交后： 事务没有完全提交，无法获取到事务结果
二阶段提交后： 2PC事务已完成，能够获取到事务结果


PostgreSQL为2PC事务创建保存事务数据的文件使其可以独立于session连接而存活，即使连接关闭也不会影响2PC事务的状态

# 提交日志 CLOG
>[!tip] 提交日志（Commit Log, CLOG），记录事务的状态，分配在共享内存，用于事务处理全过程

在逻辑上是一个数组，记录事务txid与状态，随事务变更而更新与追加
当关机或者存档刷入目录pg_xact/ 下的文件（默认256KB）中，超过用新文件
