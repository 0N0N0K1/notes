>[!tip]
>1. 索引与数据分离
>     - 主键、唯一约束都靠**独立索引**维护，数据不按主键组织 物理无序
>     - 所有索引（包括主键）叶子存的是 ctid 指针，不是主键值
>     - 查询走索引 = 索引页定位 → 拿 ctid → 回表读堆页
>     - 索引与堆是两套独立的页结构、独立的文件
>2. 追加式写
>     - INSERT = 插入只是往有空闲的页（.fsm文件）里塞，不保证任何顺序
>     - UPDATE = 插入新版本行 + 旧行打 xmax 标记
>     - DELETE = 只打 xmax，行数据原地保留
>3. MVCC 内联于行
  >    -  通过系统列xmin、xmax、ctid、t_infomask
>4. 页面自治
>     - 每个 8KB 页独立管理：头部 + 行指针数组 + tuple 区
>     - 页间无链接，全表扫描 = 顺序读所有页
>     - TOAST（超大属性存储技术）：由于页面大小固定且不允许元组跨页存储，当字段值过大时，TOAST 会先尝试压缩，如果仍然太大，则将其拆分并存储到单独的 TOAST 表中
>5. HOT 更新优化
>     - 更新不涉及索引列且新版本能放进同页 → 页内链表（旧 ctid → 新 ctid），不触碰任何索引
>6. 需要 vacuum
>     - 死行只是"标记删除"，空间不自动归还 OS
>     - autovacuum 负责标记页内空间可复用；VACUUM FULL 才重写文件收缩磁盘
>     - 不及时清理 → 膨胀 、备份变大

![[Pasted image 20260923143040.png]]
表的页面page包含了四部分：
1. 堆元组（heap tuples） —— 堆元组就是数据，从页面底部开始依序堆叠
2. 空闲空间
3. 行指针（line pointer） —— 每个行指针占4个字节，保存着指向堆元组的指针。它们也被称为项目指针（item pointer）。行指针简单地组织为一个数组，扮演了元组索引的角色。每个索引项从1开始依次编号，称为偏移号（offset number）。当向页面中添加新元组时，一个相应的新行指针也会被放入数组中，并指向新添加的元组
4. 首部数据（header data） —— 页面的起始位置分配了由结构PageHeaderData定义的首部数据。它的大小为24个字节，包含关于页面的元数据。该结构的主要成员变量为：

| page header 字段      | 作用                               |
| ------------------- | -------------------------------- |
| pd_lsn              | 唯一标识上一个写入到这个page 的请求             |
| pd_checksum         | 当前page 的校验和                      |
| pd_flags            | 当前page 的一些flag信息，是否有空,其元组是否对外可见等 |
| pd_lower            | 标识当前page 空闲空间的起始偏移位置             |
| pd_upper            | 标识当前page 空闲空间的结束偏移位置             |
| pd_special          | 特殊空间的 起始偏移位置                     |
| pd_pagesize_version | 标识page大小和当前page版本信息              |
| pd_prune_xid        | 标识本页面可以回收的 最老的元组 id              |
| pd_linp             | 可变长度的数组，存储元组在当前page内部的起始偏移地址     |

堆元组（heap tuples）结构：

| tuple字段                | 作用                                                             |
| ---------------------- | -------------------------------------------------------------- |
| len                    | 整个tuple header-data + data-area 的长度                            |
| t_self                 | 标识当前 tuple 所处的 page 位置（page的block-number 以及 page内的offset）      |
| tableOid               | 当前tuple 所处的表 的唯一标识                                             |
| HeapTupleHeader t_data | 保存整个tuple的 header 关键信息。其内部的字段与 pg 要是实现的事务语义强相关                 |

| t_xmax                 | 标识对当前元组进行更新/删除 时的事务id, 如果 t_xmax 被设置为0，则标识没有事务操作对该元素进行 更新和删除   |
| t_cid                  | 保存命令标识（command id, cid），cid意思是在当前事务中，执行当前命令之前执行了多少SQL命令，从零开始计数 |
| t_xvac                 | 标识执行 vaccum full 操作的id                                         |
| t_ctid                 | 唯一标识一个元组，如果当前元组被更新或者删除，则t_ctid 则会被更新为最新的元素的t_ctid              |
| t_infomask2            | 标识当前元组有多少列                                                     |
| t_infomask             | 存储了元组的属性flag信息，比如 当前元组是否有空列， 是否有变长的列，object-id 列是否为空等          |
| t_hoff                 | 标识整个header + 后面的bitmap的占用偏移，方便上层利用t_hoff 计算实际的data_area 数据     |
| t_bits                 | 空值位图，有null值，这里会记录，是一个变长的 bitmap数组，用来标识当前元组某一列是否为空              |
| data_area              | 元组的数据区域                                                        |

# 2. WAL及相关内容
>[!tip]
>WAL（Write-Ahead Logging，预写日志）
>是保证==崩溃恢复（Crash Recovery）和数据持久性（Durability）==的核心机制
>核心思想：==先写日志，再写数据 (随机写数据页变成顺序写日志，性能提升)==

![[Pasted image 20260923203800.png]]

| 参数                           | 默认值       | 说明                                   |
| ---------------------------- | --------- | ------------------------------------ |
| checkpoint_timeout           | 5min      | 自动检查点最大间隔                            |
| max_wal_size                 | 1GB       | WAL 达到该量会触发检查点，软限制                   |
| min_wal_size                 | 80MB      | WAL 回收下限                             |
| checkpoint_completion_target | 0.9       | 在下次检查点前用多长时间完成刷脏，0.9 表示分散到 90% 间隔内   |
| checkpoint_flush_after       | 256kB     | 每写一定量就刷盘，减少脏页堆积                      |
| checkpoint_warning           | 30s       | 检查点间隔小于该值会记警告                        |
| full_page_writes             | on        | 检查点后第一次改页会写整页到 WAL                   |
| wal_level                    | replica   | WAL 记录级别：minimal / replica / logical |
| wal_buffers                  | -1（自动）    | WAL 共享内存缓冲区大小                        |
| wal_sync_method              | fdatasync | WAL 刷盘方式                             |
| wal_compression              | off       | 是否压缩 WAL 中的整页镜像                      |
| wal_segment_size             | 16MB      | WAL 段文件大小（编译时决定）                     |
| wal_writer_delay             | 200ms     | WAL Writer 进程刷盘间隔                    |
| wal_writer_flush_after       | 1MB       | WAL Writer 强制刷盘阈值                    |
| synchronous_commit           | on        | 提交是否等待 WAL 刷盘                        |
| archive_mode                 | off       | WAL 归档开关 \|                          |
| track_wal_io_timing          | off       | 是否统计 WAL I/O 耗时                      |
| wal_consistency_checking     | 空         | 对指定表做 WAL 一致性检查                      |
| wal_debug                    | off       | 输出 WAL 调试信息（仅开发用）                    |
## LSN（日志序列号）
每条 WAL 记录都会获得一个唯一的、单调递增的 **LSN**，它本质上是 WAL 日志中的一个字节偏移量
LSN 不仅用于标识记录，还用于衡量复制和恢复的进度
## Checkpoint (检查点) 
1. 在 WAL 中写入一条 checkpoint 记录（包含 redo 起点 LSN、时间线等）
2. 把 redo 起点之前的所有脏数据页分散进行写盘
3. CLOG（事务提交状态）、multixact 等也落盘
4. pg_control里记录这次 checkpoint 的位置，下次启动从这里恢复
作用：
- 缩短崩溃恢复时间
- 推进 WAL 可回收位置，让旧 WAL 能被删除/回收
- 保证数据文件与 WAL 的一致性

 触发时机： 
- 手动执行CHECKPOINT
- checkpoint_timeout 到期
- 自上次检查点后产生的 WAL 超过 max_wal_size
- 备份相关操作：pg_basebackup、pg_start_backup
- 数据库正常关闭
## full_page_writes（全页写）
==检查点之后对每个页page的第一次写==：将该页镜像（8KB）+写的增量 记录到WAL（代价是WAL变大，）

作用：
防止checkpoint过程中宕机出现撕裂页（torn page，脏页没有完全刷盘），下次用WAL恢复以该撕裂页为基准，导致恢复数据出现错误；而full_page_writes记录了该页上个checkpoint后的初始状态可以覆盖撕裂页

## 崩溃恢复流程

数据库启动时进入恢复模式：
1. 从 **checkpoint** 记录开始（pg_control 文件中记录了 redo 起点）
2. 顺序读取该点之后的所有 WAL 记录
3. 对每条记录判断：对应的 data page 的 pd_lsn（页面上次被修改的 LSN）是否 小于 该记录的 LSN
    - 是 → 需要重放（apply）该记录
        - 用全页镜像覆盖可能损坏的页
        - 应用 WAL 中的增量变更，重建脏页
    - 否 → 该页已包含此修改，跳过
4. 重放到 WAL 末尾后，数据库达到一致性状态，进入正常运行

# 3. MVCC
>[!tip]
PostgreSQL 的 MVCC（Multi-Version Concurrency Control，多版本并发控制）
核心思想是：==写不阻塞读、读不阻塞写==
通过为==每行数据保存多个版本，不同事务看到不同时间点的数据快照，从而避免读写加锁==
xmin/xmax标记版本生命周期，t_ctid构建版本链，VACUUM异步清理旧版本，不同隔离级别仅调整快照获取时机

## 元组头部字段
1. xmin 字段记录插入该行的事务ID，作为该版本的“出生时间戳”；  
2. xmax 字段记录删除或更新该行的事务ID，值为0表示当前有效，非0则标记为逻辑删除；  
3. t_ctid 指向同一行最新版本的物理位置，形成前向版本链；  
4. t_infomask 中的 Hint Bits 缓存 xmin/xmax 对应事务的提交状态，避免频繁查 CLOG 日志
## 快照（Snapshot）
快照包含三个核心要素：
- ==快照xmin==（当前活跃事务中最小事务ID）
- ==快照xmax==（下一个待分配事务ID）
- ==快照xip 数组==（当前所有活跃事务ID列表）
## 可见性判断
MVCC 严格依据此快照与元组头部字段比对执行：
先对元组头部xmin
1. 检查 元组头部xmin 事务是否已提交：先查 Hint Bits，若未缓存则查 CLOG 提交日志
2. 若 元组头部xmin 事务未提交或已回滚→元组不可见  
3. 若 元组头部xmin ≥ 当前快照的 xmax→元组不可见

再对元组头部xmax
1. 元组头部xmax = 0 没有删除/更新/锁→元组可见。
2. 元组头部xmax= 当前事务 ID
     如果是当前事务执行的 DELETE 或 UPDATE，且命令已经生效 → 元组不可见。
     如果只是当前事务加的锁 → 元组仍可见。
3. 元组头部xmax 在 xip_list 中
     说明元组头部xmax事务在快照创建时正在进行删除/更新未生效→ 元组仍可见。
4. 元组头部xmax 不在 S.xip_list 中
     1. 元组头部xmax >= 快照xmax
         说明元组头部xmax事务 在快照创建时尚未开始 → 元组仍可见。
    2. 元组头部xmax < 快照xmax 且不在 xip_list，查 CLOG 提交日志
         已提交，删除/更新生效 → 元组不可见
         已回滚，删除/更新无效 → 元组可见
     3. 元组头部xmax <快照xmin，同样查 CLOG 提交日志判断提交还是回滚
 
## 隔离级别
各隔离级别不改变底层版本存储方式，仅改变事务视角

| 级别                | 说明                                         |
| ----------------- | ------------------------------------------ |
| READ COMMITTED    | 每次查询语句开始时重新获取快照，因此同一事务内多次 SELECT 可能返回不同结果  |
| REPEATABLE READ   | 事务启动时获取一次快照并全程复用，保证多次读取结果一致                |
| SERIALIZABLE      | 在 REPEATABLE READ 基础上增加谓词锁与冲突检测，防止幻读与序列化异常 |
|  READ UNCOMMITTED | 不支持                                        |

## vacuum
VACUUM命令用于回收死元组（dead tuples）占用的存储空间
在PostgreSQL中，被删除或更新废弃不再被引用的元组并没有在物理上从它们的表中移除，将存在直到VACUUM被执行
==导致表与索引膨胀==

```sql
VACUUM [ FULL ] [ FREEZE ] [ VERBOSE ] ANALYZE [ table_name ]
```
FULL选项会执行更广泛的处理，包括跨块移动行以压缩表，但会锁定整个表
FREEZE选项用于冻结旧的事务ID，防止事务ID包裹问题
VERBOSE选项会显示详细的清理工作报告 
ANALYZE选项用于更新查询优化器的统计信息 
table_name是指要清理的表的名称，未加则VACUUM会处理当前数据库中的所有表

1. VACUUM:
     - 回收表中的死数据，即已经被删除或更新但尚未移除的数据
     - 将这些死数据标记为可重用，将来插入新数据时可以重用空间
     - ==操作过程不会锁定表==，因此可以与其他操作并行进行
2. VACUUM FULL:
     - 不仅执行常规VACUUM的功能，还会重新组织表中的数据，将有效数据移动到表的开头，释放表末尾的空页
     - ==操作过程会锁定表==，因此在执行期间不能对表进行访问

autoVacuum功能:
    autovacuum是一个自动执行VACUUM和ANALYZE命令的系统辅助进程它的主要目的是:
    - 回收被标识为删除状态的空间，确保数据库性能不会因为数据膨胀而下降
    - 更新表的统计信息
    - 防止事务ID回卷
```
 autovacuum：控制是否启动系统自动清理功能，默认值为on
 autovacuum_max_workers：设置系统自动清理工作进程的最大数量
 autovacuum_naptime：设置两次系统自动清理操作之间的间隔时间
 autovacuum_vacuum_threshold和 autovacuum_analyze_threshold：设置当表上被更新的元组数的阈值，超过这些阈值时分别需要执行vacuum和analyze
 autovacuum_vacuum_scale_factor和autovacuum_analyze_scale_factor：设置表大小的缩放系数
 autovacuum_freeze_max_age：设置需要强制对数据库进行清理的XID上限值
```

# 4. 锁
## 表级锁（Table-Level Locks）
表级锁作用于整个数据表。当需要对整个表进行操作，如`CREATE INDEX`或`DROP TABLE`时，会使用表级锁

| 锁                           | 说明                                                                  |
| --------------------------- | ------------------------------------------------------------------- |
| ACCESS SHARE LOCK           | 用于数据查询(SELECT)，与ACCESS EXCLSIVE锁冲突                                  |
| ROW SHARE LOCK              | 用于SELECT FOR UPDATE或SELECT FOR SHARE，与EXCLUSIVE和ACCESS EXCLUSIVE锁冲突 |
| ROW EXCLUSIVE LOCK          | 用于数据的更新、插入和删除操作，与SHARE、SHARE ROW EXCLUSIVE和ACCESS EXCLUSIVE锁冲突      |
| SHARE LOCK                  | 用于创建索引（CREATE INDEX），防止并发的数据变更                                      |
| SHARE ROW EXCLUSIVE LOCK    | 用于某些不会自排他的操作，比如创建触发器                                                |
| EXCLUSIVE LOCK              | 用于防止并发的数据变更和读取操作，只允许并发的ACCESS SHARE锁                                |
| ACCESS EXCLUSIVE LOCK       | 用于TRUNCATE、DROP TABLE等DDL操作，与其他所有锁冲突                                |
| SHARE UPDATE EXCLUSIVE LOCK | 用于VACUUM和某些ALTER TABLE操作，防止并发的schema改变和VACUUM命令                     |
## 行级锁（Row-Level Locks）
行级锁是PostgreSQL中最细粒度的锁。它们作用于数据表中的单个行，允许多个事务同时修改不同的行，从而最大化并发性

| 锁                 | 说明                                        |
| ----------------- | ----------------------------------------- |
| FOR UPDATE        | 对整行进行更新，包括删除行，阻止其他事务对行的读取和更新              |
| FOR NO KEY UPDATE | 对除主(唯一)键外的字段更新，对行加锁，但允许其他事务在不锁定键值的情况下进行更新 |
| FOR SHARE         | 读该行，不允许对行进行更新，阻止其他事务对行的更新                 |
| FOR KEY SHARE     | 读该行的键值，但允许对除键外的其他字段更新，主要用于外键检查            |
## 页级锁（Page-Level Locks）
页级锁介于行级锁和表级锁之间，作用于数据表中的单个数据页。它们常用于索引操作和批量数据修改,页级锁用于控制对数据页的并发访问

| 锁             | 说明                  |
| ------------- | ------------------- |
| WALInsertLock | 向WAL缓冲区写入WAL记录时需要的锁 |
| WALWriteLock  | 确保WAL数据被刷入磁盘的锁      |
| ProcArrayLock | 用于追踪正在运行的后端进程和事务    |
## 咨询锁（Advisory Locks）

询锁是一种用户控制的锁，用于应用程序级别的锁定。它们不与特定的数据库对象关联，而是由应用程序根据需要获取和释放
咨询锁可以是会话级别的或事务级别的，允许用户在不同的进程或事务之间进行协调

## 死锁（Deadlocks）

死锁发生在两个或多个事务相互等待对方持有的锁时。
PostgreSQL有参数如`lock_timeout`、`deadlock_timeout`和`log_lock_waits`来控制死锁的检测和处理。
