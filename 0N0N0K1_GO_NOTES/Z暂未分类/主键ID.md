# 1. 问题

在一些场景下我们希望各每个对象分配一个全局唯一ID，用以区分和查找对象，同时希望当储存在数据库中时，这个ID能够做该对象的主键（退一步来说唯一索引也行），这就对ID产生方案有了如下约束 ：
1.  全局唯一： 单机则单机产生唯一，分布式下则多实例产生都唯一
2. 长度越短越好：128bits肯定不如64bits节约空间
3. 时间有序： ID具有可比性，且随时间增大，避免插入表时挤入老对象中间导致大规模移动
4. 重启保障不重复：不能因为一次重启就导致重复的可能
5. 每秒生成ID多：能够处理高并发生成
6. 安全：尽量不暴露敏感数据

# 2. 常见ID方案综述

1. 数据库（如：MySQL）默认主键：
    - 优点
        - 自增，时间有序
        -  不用维护，重启不影响
    -  缺点
        - 暴露业务量
         - 不受控制，即插入对象后其分配的ID要查数据库才能确定
         - 每秒ID数少，高并发表现差
         - 迁移数据的同时插入数据可能会导致旧数据ID冲突
         - 多库、多表、多实例时难以协调

 2. Redis INCR/INCRBY
    - 优点
        - 自增，时间有序
        - 能够插入前得到分配的ID
        -  基于内存操作快，每秒ID数多
        - redis 命令处理单线程，并发安全
    -  缺点
         - 每次申请ID都要往返一次,QPS受限于网络往返（可通过批量取解决）
         - 需要开启持久化储存自增数据，会导致性能下降且仍有丢失风险，重启可能导致重复

# 3. UUID
UUID 是一个 ==128 bits== 值，各版本特性不一致
一般表示为 32 十六进制数，连字符分隔，表示为(其中 M 表示版本，N 表示变体):
```text
xxxxxxxx-xxxx-Mxxx-Nxxx-xxxxxxxxxxxx
```
##  V1/6
基本无使用场景  
### 布局：
- 60 bits  时间戳（100 纳秒间隔，从 1582-10-15 起算)
- 14 bits  时钟序列（防时钟回拨重复）
- 48 bits  节点标识（通常为 MAC 地址）
### 缺点：
-  会暴露 MAC 地址和生成时间，隐私差
- V1 时间低位在前不是时间顺序;  V6高位在前无此问题
- 时钟回拨时需要时钟序列处理重复

## V2
基本无使用场景

## V 3/5
适用于需要确定性命名映射
### 特性
命名空间 + MD5（V3）/ SHA-1 (V5)
UUID = MD5/SHA-1(namespace_uuid + name)
namespace_uuid:
DNS：6ba7b810-9dad-11d1-80b4-00c04fd430c8
URL：6ba7b811-9dad-11d1-80b4-00c04fd430c8
OID：6ba7b812-9dad-11d1-80b4-00c04fd430c8
X.500：6ba7b814-9dad-11d1-80b4-00c04fd430c8

相同输入永远得到相同输出——确定性 ID：
```go
dns := uuid.MustParse("6ba7b810-9dad-11d1-80b4-00c04fd430c8")
id := uuid.NewMD5/SHA(dns, []byte("www.example.com"))
// 永远是: 5df41881-3aed-3515-88a7-2f4a814cf09e
```
###  优点
- 相同命名空间 + 相同名称，总是生成相同 UUID
###  缺点
- 因为其特殊性，故使用场景受限（如生成做主键的ID）
## V4*
适用于 TraceID、SessionID、对外暴露且无需排序的标识
### 布局:
122 bits 随机数
6 bits 版本和变体占据
```go
id := uuid.New() // v4
```
### 优点
- 完全不可预测，无隐私泄露
- 碰撞概率：生成 10 亿个 UUID，碰撞概率约 十亿分之三
### 缺点
- 完全无序，数据库索引灾难（B+ 树随机插入导致页分裂、缓存失效）
## V7*
### 适用于
- 主键
- 日志、事件 ID
- 需要时间排序的分布式 ID
### 布局：
48 bits Unix 毫秒时间戳 
4 bits 版本 
12 bits  rand_a 
2 bits 变体 
62 bits  rand_b
### 优点：
- 时间排序
- 时间戳到约 10889 年
- 同一毫秒内可用 rand_a 做计数器，保证单调递增
### 缺点：
- 会暴露创建时间
- 随机部分仍需安全随机源

# 4. snowflaken ID*

snowflake ID 是一个64bits的值，该分布式ID生成算法由Twitter开源

### 布局：
```
 1 位        41 位                   10 位          12 位
┌────┬───────────────────────┬─────────────────┬────────────┐
│  0 │      时间戳（毫秒级）   │      节点ID     │   序列号    │
└────┴───────────────────────┴─────────────────┴────────────┘
符号位(恒0)  从自定义纪元起算           0~1023       0~4095
```
- 1 bit 保留为0  
- 41 bits 时间戳（ms级可以使用≈ 69.7 年）
- 10 bits 机器标识(最多支持部署1024个节点)  
- 12 bits 毫秒内计数序列号（每个节点每ms最多4096个ID序号）

### 优点
- 高性能、本地生成无网络开销
- 趋势递增（ms内不是严格递增），索引友好
- 64 位整数，紧凑高效，优于uuid
- 包含时间信息与生成服务器ID
- 支持多节点，分布式友好
### 缺点
- 依赖时钟，有回拨问题
- 包含时间信息与生成服务器ID
- 需要预分配机器ID，管理有成本


# 5. XID
XID 是一个 96 bits 的值， 其核心算法借鉴自 MongoDB 的 ObjectID
编码结果仅包含小写字母 a-v 和数字 0-9编码后为一个 20 字符 的字符串，如：
```
 ad56cv756vaacffhjk6e
```
### 布局

```
     32bits       24bits      16bits     24bits   
┌─────────────┬────────────┬─────────┬────────────┐
│    时间      │   机器ID   │  进程ID  │   序列号   │
└─────────────┴────────────┴─────────┴────────────┘
  秒级          跨机器唯一     0~131071   0~16777216
```

- 32bits 时间戳（s级）
- 24 bits 机器标识(最多支持部署16777216个节点)
- 16 bits 进程 ID(最多支持部署131072个进程)  
- 24 bits 秒内计数序列号（每个节点进程每s最多16777216个ID序号）

### 优点 
- 字符集：仅包含小写字母 a-v 和数字 0-9，不含大小写敏感字符和特殊符号，避免了系统间传输时可能出现的转义或大小写问题
- 时间有序
- 进程粒度做区分
### 缺点
- 非加密安全：XID 的生成依赖于系统时间和可预测的计数器
- 秒级精度：时间戳仅精确到秒，在高并发下，同一秒内生成的 ID 顺序由计数器决定，严格来说并非全局严格递增，而是秒间递增
- 需要预分配机器ID，管理有成本
