| 分类                           | 代表方法                                                    | 行为                         |
| ---------------------------- | ------------------------------------------------------- | -------------------------- |
| **链式方法** Chain Method        | Where、Select、Omit、Joins、Preload、Scopes、Clauses          | 只往 Statement 里追加条件，不执行 SQL |
| **终结方法** Finisher Method     | Create、First、Find、Take、Save、Update、Delete、Scan、Row、Rows | 立即执行 SQL，触发HOOK            |
| **新会话方法** New Session Method | Session、WithContext、Debug                               | 返回可安全复用的新 *gorm.DB         |

# 1. 条件污染
>[!warning] 链式方法Chain Method 或 终结方法Finisher Method 
>之后返回已初始化的 *gorm.DB 实例，其无法安全地重新使用，因为它可能会将先前操作中的状况带回，有可能导致被污染的 SQL 查询

```go
queryDB := DB.Where("name = ?", "jinzhu")

// First query
queryDB.Where("age > ?", 10).First(&user)
// SQL: SELECT * FROM users WHERE name = "jinzhu" AND age > 10

// Second query with unintended compounded condition
queryDB.Where("age > ?", 20).First(&user2)
// SQL: SELECT * FROM users WHERE name = "jinzhu" AND age > 10 AND age > 20

// 事务回调里的 `tx` 复用尤其危险
db.Transaction(func(tx *gorm.DB) error {
    tx.Where("id = ?", 1).First(&a)
    tx.Where("id = ?", 2).First(&b)
    // 第二次查询实际条件：id = 1 AND id = 2 → 查不到，难排查！
    return nil
})
```
# 2.  安全复用的三种方式
>[!tip] **新会话方法** New Session Method 
>Session、WithContext、Debug  返回一个"标记为可安全复用"的*gorm.DB 实例每次链式调用都基于当前条件新建 Statement，终结方法执行完不残留状态                         

```go
// 方式1：Session（最常用）
queryDB := db.Where("name = ?", "jinzhu").Session(&gorm.Session{})

// 方式2：WithContext（顺带传 ctx）
queryDB := db.Where("name = ?", "jinzhu").WithContext(ctx)

// 方式3：Debug（顺带开日志）
queryDB := db.Where("name = ?", "jinzhu").Debug()


queryDB := db.Where("name = ?", "jinzhu").Session(&gorm.Session{})

queryDB.Where("age > ?", 10).First(&user)
// WHERE name = "jinzhu" AND age > 10 

queryDB.Where("age > ?", 20).First(&user2)
// WHERE name = "jinzhu" AND age > 20 （不带 age > 10）
```

# 3. 总结

规则 1：从 初始连接返回 `db` 直接开始的链是安全的
规则 2：链式方法的结果，不能跨"逻辑操作"复用
规则 3：Finisher 执行后，实例进入"不可复用"状态

>[!tip]
Generics API 的每个操作都接收 ctx、返回 error，设计上天然隔离了 Statement 状态——这正是文档把它列为 Traditional API 替代方案的原因
