# 2.  AMQP 0-9-1 模型
**AMQP（Advanced Message Queuing Protocol，高级消息队列协议）** 是一种面向消息中间件的开放应用层协议，常用于系统之间的异步通信、解耦、削峰和可靠消息投递。它是**二进制、基于 TCP 的线级协议**，不是某个语言独有的 API，因此不同语言、不同厂商的实现理论上可以互通。
## 2.1 流程概览

1. 生产者通过TCP连接 Broker，认证并打开 Channel
2. 声明 Exchange、Queue、Binding
3. 生产者推送消息到 Exchange
4. Exchange 根据 routing key 和 binding 路由到 Queue
5. 消费者从 Queue 拉取消息
6. 消费成功后发送 ack
7. 如果消费完成不再使用需关闭Chan或者Conn,以防止丢失连接的句柄出现僵尸消费者

## 2.2 核心概念

|        对象        | 作用                                                                                                                                       |
| :--------------: | :--------------------------------------------------------------------------------------------------------------------------------------- |
|   **Message**    | 包含 payload （ 存放生产者实际发送data ） +  label（ 附加标签，用于路由等，不会被消费者获得 ）两部分                                                                          |
|   **Producer**   | 生产Message ，通过 chan publish 到指定 exchanger 上，对于producer不用关心谁是消费者，不用关心消息是否被消费                                                               |
|   **Publish**    | 指Producer将Message发送到exchanger的动作                                                                                                         |
|   **Channel**    | 应用进程只用建立==一个与RabbitMQ Server 的 TCP 连接==，后续充当producer/consumer的协程/线程只需要==复用TCP连接==建立AMQP Channel即可，channel彼此独立，在queue眼中一个消费者是一个活跃的channel |
|  **Exchanger**   | 接收producer publish 的消息 并根据其中 router key 转发到相应的binding在自身的队列中                                                                             |
|     **Bind**     | Queue通过router key 绑定到exchanger上                                                                                                          |
|    **Queue**     | 接收exchanger转发的消息并暂存，等待consume                                                                                                            |
|   **Consumer**   | 从指定Queue中consume消息                                                                                                                       |
|   **Ack/Nack**   | consumer响应是/否接收并成功处理该消息，决定queue是/否指针移动下一条消息<br>- ack: 该消息成功接收并处理，下次消费为下一条消息；<br>- navk: 下次消费为依旧为该条消息；                                    |
|   **confirm**    | 反馈给producer消息是否成功 到达交换机+到达指定队列+持久化                                                                                                       |
| **Virtual Host** | 一个RabbitMQ Server 可建立多个vhost，在逻辑上隔离空间，不同 vhost 之间队列、交换机等互不影响                                                                             |
| **Routing Key**  | 路由键，交换机据此决定消息去向                                                                                                                          |
|  **Connection**  | 客户端与 Broker 之间的 TCP 连接                                                                                                                   |
|    **Broker**    | 消息中间件服务器，如 RabbitMQ                                                                                                                      |
## 2.3 消息结构

AMQP 0-9-1 的消息不是一个大包，而是由帧组成：
1. **Method 帧**：如 `basic.publish`，包含 exchange、routing key、mandatory 等。
2. **Header 帧**：消息属性，如 delivery-mode、priority、expiration、message-id、correlation-id、headers。
3. **Body 帧**：真正的消息体，可以是任意二进制，可能分成多个帧。
4. 
关键属性：

| 属性                                  | 作用                              |
| ----------------------------------- | ------------------------------- |
| `delivery-mode`                     | 1 非持久化，2 持久化                    |
| `message-id`                        | 业务消息唯一 ID，常用于去重                 |
| `correlation-id`                    | RPC 请求响应关联                      |
| `reply-to`                          | 回复队列                            |
| `expiration`                        | 消息 TTL，毫秒字符串                    |
| `priority`                          | 优先级                             |
| `headers`                           | 自定义头，可用于 headers exchange 或业务标记 |
| `content-type` / `content-encoding` | 内容类型和编码                         |
| `timestamp`                         | 时间戳                             |
| `app-id` / `user-id`                | 应用和用户标识                         |

# 3. 可靠性机制
| 风险环节         | 导致原因           |
| ------------ | -------------- |
| 生产者 → Broker | 网络丢、Broker 未收到 |
| Broker 存储    | 宕机、磁盘故障        |
| Broker → 消费者 | 消费者崩溃、处理失败     |
| 重复           | ack 丢失、重发      |
| 顺序           | 多消费者、重试        |
## 3.1 持久化
写入磁盘，==防止服务器重启后丢失==，但会因此影响性能

Broker 重启后消息还在需要：
1. Exchange 声明为 `durable=true`
2. Queue 声明为 `durable=true`
3. 消息发送时 `delivery-mode=2`

| 对象        | 持久化方法                                                         |
| --------- | ------------------------------------------------------------- |
| exchanger | 创建时指定持久化    ![[Pasted image 20260910212446.png\|428]]         |
| queue     | 创建时指定持久化            ![[Pasted image 20260910212659.png\|419]] |
| message   | 生产者publish时指定持久化durable：true                                  |

## 3.2 生产者 Confirm 机制

确保==反馈给producer消息是否成功 到达交换机+到达指定队列+持久化==

开启confirm后会为每条消息附加唯一ID

生产者程序要处理：推荐异步处理 confirm 的返回
考虑对confirm的返回进行  消息ID管理、超时处理、重发等处理
![[Pasted image 20260910213231.png|480]]

AMQP 0-9-1 支持 tx.select、tx.commit、tx.rollback。它可以保证发布和 ack 的原子性（可回滚），但性能差、容易阻塞，通常不推荐。Publisher Confirm 更轻量。

## 3.3 消费者手动 Ack 机制

==反馈给queue消息是否成功接收并处理==

- autoAck=true：Broker 投递后立即删除消息。消费者处理失败就丢了。
- autoAck=false：消费者处理完后手动 `basic.ack`，Broker 才删除。

 ack / nack / reject
- basic.ack：确认成功，Broker 删除消息。
- basic.nack：RabbitMQ 扩展，可批量拒绝，支持 requeue。
- basic.reject：拒绝单条，支持 requeue。

如果 requeue=true，消息重新入队，可能再次投递，并带 redelivered=true。

## 3.4 消费者幂等性实现

- 生产者重发
- confirm 丢失
- 消费者处理成功但 ack 丢失
- 消费者断开，未确认消息重新入队
会导致==已处理消息重发==

所以实际系统消费端要实现==幂等==（同一操作即消费同一条消息，执行一次和执行多次，对系统状态/结果的影响相同）

实现幂等/去重方法
- 数据库唯一键
- Redis setnx
- 业务状态机
- message-id + 消费记录表
## 3.5 消费者QoS / prefetch

basic.qos(prefetch_count=N) 限制==消费者未确认消息数量==
- 防止消费者被压垮
- 更公平地分发
- 减少内存占用
prefetch=0 表示无限制，通常不推荐。

## 3.6 保证消息顺序性

但以下会破坏顺序：
- 多消费者
- 重试 / requeue
- 网络分区
- 消息过期

需要严格顺序时：
- ==单活消费者==
- ==实现幂等性==
- ==业务层自己排序==

## 3.7 死信队列+延时重试

消息进入死信的条件：
- 被 reject / nack 且 requeue=false
- 消息 TTL 过期
- 队列超过最大长度
- Quorum Queue 超过 delivery limit

延时重试流程：
1. 消费失败，nack 且不 requeue，进入死信交换机。
2. 死信队列设置 TTL，过期后通过 DLX 回到原队列。
3. 重试多次后进入最终死信队列，人工处理。

 可用 x-delivery-limit 限制投递次数，防止毒消息无限循环

## 3.8 TTL（可选）

- 消息 TTL：x-message-ttl 或消息属性 expiration
- 队列 TTL：x-expires，队列未使用后自动删除

懒删除： 消息过期不一定立即删除，可能在到达队头或消费时才处理。
