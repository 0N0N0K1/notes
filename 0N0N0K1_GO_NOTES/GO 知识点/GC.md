# 1. 核心概念
## 1.1 三色标记

| color | 含义              |
| ----- | --------------- |
| 黑     | 可达对象，其指向对象已全标记  |
| 灰     | 可达对象，其指向对象未完成标记 |
| 白     | 未被标记，可能是非可达对象   |
标记流程：
1. 初始全白，扫描根（栈、全局变量、寄存器），把根直接指向的对象置灰（对象所在mspan中gcmarkBits=1并放入灰队列）
2. 从灰队列拿出灰对象遍历所指对象置灰，灰对象所有所指对象置灰后，自身置黑（移除灰队列）
3. 灰队列中没有对象时，扫描完成，回收白色对象
## 1.2 混合写屏障

GC三色标记期间
栈对象：
- 栈上初始以及新对象没有混合写屏障，可默认视为黑
堆对象：
- 插入屏障：当黑色对象尝试引用堆上白色对象时，将该白色对象置灰
- 删除屏障：当一个堆上白色对象被删除引用时，将该白色对象置灰
-  堆上新建对象置灰

解决问题：
1. 并发三色标记 GC 中对象被漏标误回收的问题
    GC 并发标记时，用户 goroutine 还在修改指针，可能出现：
    黑色对象新增指向白色对象的引用，同时灰色对象删除指向白色对象的唯一引用  
    白色存活对象被漏标，最终被错误回收
2. STW过长问题
    使用纯插入屏障时，栈上写操作不受保护，所以标记结束必须 STW 重扫所有 goroutine 栈

保留问题：
     不可达对象本轮GC可能不被清理
     
## 1.3 并发协作

1. GC协程工作期间不会完全暂停用户协程，而是并发进行

2. 用户协程也会参与 GC，通过两种方式配合：
    - 写屏障 
    用户协程写指针时触发混合写屏障，把旧对象或新对象标灰，保证三色不变式，防止存活对象被漏标。
    -  辅助标记（mutator assist）  
    如果用户协程分配内存太快，GC 标记进度落后，用户协程会被征召去执行 gcAssistAlloc（[[GMP#2.3.3 抢占式让渡]]），帮忙标记对象“还债”。  
    这时用户协程会临时变成 GC 的一部分，表现为业务代码变慢。
    
3. STW 阶段：全部暂停
    GC 开始和标记终止时会有短暂（us级）的 **STW**。  
    这时所有用户协程都会被暂停，GC worker 也停止运行，由 runtime 统一控制。 
     
4. GC 需要扫描用户协程的栈时，会抢占（[[GMP#2.3.3 抢占式让渡]]）用户协程，防止GC长时间等待用户协程，而用户协程被抢占的时间通常很短

# 2. GC流程
## 2.1 触发阶段

 三种触发方式

| 方式        | 说明                                            |
| :-------- | :-------------------------------------------- |
| **堆增长触发** | 当前存活堆大小 × (1 + GOGC/100)。默认 GOGC=100，即堆翻倍时触发  |
| **定时触发**  | [[sysmon]]监视距上次 GC 超过 2 分钟强制触发，防止长期无分配导致内存不回收 |
| **手动触发**  | runtime.GC() 或 debug.FreeOSMemory()           |

Pacing（调步）
- 决定何时启动标记已经后台标记 worker 数量，控制CPU占用25%左右
- mutator assist比例：用户分配越快，assist 越重
如果估算失败，用户协程会在 `mallocgc` 时被强制"执行标记工作，表现为分配延迟飙升


## 2.2 标记准备

Step 1.  STW:停止所有 goroutine : 保障所有 P 一致的状态下原子切换写屏障的开关

Step 2.  完成上一轮残余清扫（Sweep Termination）

Step 3. 打开混合写屏障（Hybrid Write Barrier）

Step 4. 启用标记辅助（Mutator Assist）                   

Step 5. 启动后台标记 worker（Mark Worker）          

Step 6.  准备根扫描任务：全局变量、所有 goroutine 栈标记为需要扫描，后续并发阶段逐个处理
## 2.3 并发标记阶段

STW 结束，用户代码恢复运行，标记与用户程序**完全并行/发**。

| 执行者                   | 说明                             |
| :-------------------- | :----------------------------- |
| **Dedicated Worker**  | 每个 P 上绑定的后台标记协程，专职做标记工作        |
| **Fractional Worker** | 按 pacing 计算出的部分 CPU 时间片，动态调整   |
| **Mutator Assist**    | 用户协程分配内存时，若 GC 落后，强制其执行标记工作    |
| **栈扫描**               | 每个 goroutine 的栈被扫描时，将其指向的堆对象置灰 |

Step 1: 根扫描
  - 全局变量 
  - 每个 goroutine 栈 
  - 寄存器
  
Step 2: 灰队列消费

Step 3: 写屏障保护（与用户代码并发）
  
step 4: 标记终止
    全局 work queue 为空
    且 所有本地 work queue为空
    且 写屏障已没有待处理的 shade 请求
    且 所有 goroutine 栈已扫描完毕

## 2.4 标记终止


  Step 1. 再次 STW，停止所有 goroutine：关闭写屏障同样需要全局一致性
  
  Step 2. 确认灰队列彻底为空          
  
  Step 3. 关闭混合写屏障                                
      
  Step 4. 统计本轮存活堆大小（live heap）          
    
  Step 5. 计算下一轮 GC 触发阈值（heap goal）   
      
  Step 6. 重置标记状态，准备清扫  


## 2.5 并发清扫阶段

1. STW 结束，进入清扫。黑色对象 = 存活，白色对象 = 垃圾

2. 清扫前上一轮的 gcmarkBits 变成下一轮的 allocBits，不需要遍历所有对象清零标记位
3.  Go 不立即回收所有白色对象，而是**惰性清扫（lazy sweep）**
    [[内存分配#2. 对象分配流程]]小对象时到 mcentral 也没有，触发 span 的清扫
     - 检查该 span 的 allocBits（上一轮标记结果）
     - 白色对象对应的槽位标记为空闲
     - 清扫后的 span 加入 mcentral 空闲链表

# 3. GO1.26+  Green Tea GC 的变化

问题：==cache miss==
传统 GC并发标记阶段按对象扫描，跨对象随机访问，CPU频繁在不同内存地址间跳跃，
与现代CPU的设计理念背道而驰。现代CPU依赖缓存提升性能：访问缓存的速度是主内存的100倍，且缓存会自动预加载最近访问内存的相邻数据。但传统GC的遍历毫无规律


Green Tea GC：==按 page 页 顺序扫描，提升缓存局部性==

1. 每个对象状态：
    - Seen：标记该对象是否被指针指向（即是否可达）。
    - Scanned：标记该对象的指针是否已被遍历。
    页面被加入工作列表后，GC会一次性扫描所有 seen=1&&scan=0 的对象，
    无需逐个处理单个对象的入队出队，大幅减少开销


2. Green Tea的标记过程核心分为三步：
    1. *根节点遍历，标记页面：从根节点出发，找到第一个可达对象后将其所在的**整个页面**加入工作列表，并设置该对象的“Seen位”
    
    2. 批量扫描页面：处理工作列表时，GC会一次性扫描页面内所有“Seen=1、Scanned=0”的对象，遍历它们的指针，将指向的其他对象所在页面加入工作列表（已在列表中的页面无需重复添加，仅更新页面内对象的Seen位)
    
    3. 完毕扫描，更新状态：扫描完一个页面的所有目标对象后，将这些对象的“Scanned位”设为1，避免重复处理。
    
    ==同一页面内的对象被批量处理，CPU缓存能充分发挥作用扫描能命中缓存，无需等待主内存==

3. 向量加速
    现代x86 CPU的AVX-512指令集支持512位宽的向量寄存器
    用向量指令一次性对比整个页面的Seen和Scanned位图，快速筛选需要扫描的对象
    彻底发挥了现代CPU的硬件优势
